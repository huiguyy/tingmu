# 听幕·方言支持与说话人分离能力调研（2026-10-30）

> 背景：用户问两个问题——①现用模型对方言支持如何？②能否区分谁在说？
> 本文全部结论均有本地实测支撑，模型/音频均从官方 release 下载，未凭印象推断。
> 目的：为"只做一件事"的边界决策提供依据——**结论：不扩项目，但方言是必须补的缺口。**

---

## 〇、现用模型是什么（先厘清，避免"大模型"误解）

听幕当前**没有 LLM**，是两个端侧神经网络模型：

| 角色 | 模型 | 体积 | 形态 |
|---|---|---|---|
| 主识别 | `streaming-zipformer-small-ctc-zh-int8-2025-04-01` | 25MB | **流式** zipformer2 + CTC，int8，纯 CPU |
| 备用识别 | `zipformer-zh-14M-int8-2023-02-23` | 24MB | 流式 transducer，int8 |
| VAD | Silero VAD | 632KB | 判断语音起止 → 驱动左上角蓝点 |

全链路**零网络请求**：模型在 APK 内，推理在手机 CPU，音频不外传。这是产品的信任基础。

## 一、方言支持：现用模型实测不合格（严重缺口）

### 1.1 实测方法

用 sherpa-onnx 官方随模型发布的**方言测试音频**（3-sichuan / 5-henan / 4-tianjin，
来自 `sherpa-onnx-paraformer-zh-small-2024-03-09/test_wavs`），
以及更严格的 `sherpa-onnx-paraformer-zh-int8-2025-10-07` 附带的
**16 段带标注川渝方言音频**（WenetSpeech-Chuan 数据集，西工大 ASLP-lab 开源）。
同音频、同样 100ms 分块流式喂入，对比各模型输出。

### 1.2 结果 A：现用模型在方言上几乎全错

同一段四川话，标准答案来自官方文档标注：

**样本 7.wav**　标准：`他坐在椅子上，挺直起腰杆，脸上展现出灿烂的笑容。`
- 现用 small-ctc-zh-2025：`他走在衣字上听自气摇脸上展现出长那米小容` → **CER 57.1%**
- 方言专用 paraformer-2025-10-07：`他坐在椅子上挺直起腰杆脸上展现出灿烂的笑容` → **CER 0.0%**

**样本 14.wav**　标准：`两岸猿声啼不住，有家难回车里住。`
- 现用 small-ctc-zh-2025：`良俺生不足有家会财力` → **CER 78.6%**
- 方言专用 paraformer-2025-10-07：`两岸猿声啼不住有家难回车里住` → **CER 0.0%**

其余 14 段（1/2/4/5/6/8/9/10/11/12/13/15/16）逐条肉眼对比，**现用模型全部出现大面积错字**，
典型：段 8「换起旅游无限的感慨…」→「燃气炉五贤力感慨斯他加同恨管场里杸五种」。

**结论：现用模型是纯普通话模型，遇方言几乎不可用。** 而听障用户的日常对话里，
方言占比远高于"普通话办公室会议"——这不是边缘场景，是主场景。

### 1.3 结果 B：候选方言模型横向对比（同一批 3-sichuan/5-henan/4-tianjin）

| 模型 | 体积 | 流式? | 四川话输出 | 河南话输出 | 天津话输出 | RTF(Mac) |
|---|---|---|---|---|---|---|
| **现用** small-ctc-zh-2025 | 25MB | ✅流式 | 「子急就是在那个…很真式」 | 「他这个意象都通到优秀…揠子」 | 「其实他就是那每个人都可以收法…」 | 0.027 |
| **TeleSpeech** ctc-int8 | **341MB** | ❌**仅离线** | 「自己就是在那个…很真实样的」 | 「他这个管一想都通到…」 | 「他就每个人手法就这思法律意…」 | 0.076–0.091 |
| **SenseVoice** int8-2025-09-09 | **237MB** | ❌仅离线 | 「自己就是在那个…就是好像很真实一样你知道吧」 | 「他这个管一向都通到…」 | 「实他就是话每个人都会以守法…也不顾及到别人的感受」 | 0.049–0.062 |
| **paraformer-zh-int8-2025-10-07**（WenetSpeech-Chuan） | **238MB** | ❌仅离线 | 「他坐在椅子上挺直起腰杆脸上展现出灿烂的笑容」✅ | — | — | 0.034–0.047 |

### 1.4 关键结构性问题：方言候选**全部不是流式模型**

sherpa-onnx python API 实测：
- `OnlineRecognizer.from_zipformer2_ctc / from_transducer / from_paraformer / from_wenet_ctc ...`
- `OfflineRecognizer.from_telespeech_ctc` ← **仅离线**
- `OfflineRecognizer.from_sense_voice` ← **仅离线**
- `OfflineRecognizer.from_paraformer`（2025-10-07 川渝版）← **仅离线**

TeleSpeech 直接以 zipformer2-CTC 加载会报错：
`'encoder_dims' does not exist in the metadata`（其 model_type 是 `telespeech_ctc`，
不是 zipformer2_ctc，不能走在线 CTC 通道）。

**但这不构成否决理由**——因为听幕本来就用 **Silero VAD 切分语音段**：
VAD 已能给出每段话的起止边界，离线模型只需对**单段话**（通常 2–10 秒）做识别，
效果与流式等价。sherpa-onnx 官方 VAD+ASR 示例正是这个组合。
**代价：单句出字延迟 = 一句话说完的时长**（VAD 静音判定 ~0.25–0.5s + 整段推理 RTF 0.04 × 段长）。

对听障场景这个代价可接受吗？→ **取决于用词习惯**：如果一句话说完才出字，
听障用户跟对话会非常难受（字追不上话）。**这是方言方案最大的待验证风险，必须真机测。**

可行的折中：**主模型保持流式普通话档（低延迟即时出字），方言档作为"可选模型"**
（用户按需切换，代价是整句出字）。这正好落在现有 `ModelEntry` 架构里——
模型选择 UI 已经有了，只需再加一档。

### 1.5 许可风险（必须记录）

- **TeleSpeech** 附带《TeleSpeech模型社区许可协议.pdf》——**社区许可，非标准开源许可**，
  商用需逐条核对协议条款。
- **WenetSpeech-Chuan / paraformer-2025-10-07**：上游 ASLP-lab 开源数据集，
  需核对 ASR 模型本身的许可。
- **SenseVoice**：FunAudioLLM/SenseVoiceSmall，Apache-2.0 系，需核对。
- 分段模型 pyannote segmentation-3.0：**MIT**（LICENSE 已确认，CNRS 2022）。
- 嵌入模型 3dspeaker eres2net：需核对 3D-Speaker 许可。

**未核对完许可前不得进入商用分发。**

### 1.6 方言方案的一句话结论

> 现用模型**不支持方言，实测 CER 57–79%，不可用**。
> 有成熟方言模型（238MB，离线，WenetSpeech-Chuan 训练，官方标注样本 CER 0%），
> 但体积是现用模型的 9.5 倍、且只能整句出字。
> **且缺可信的方言数据支撑**——它只能解决"听得准"，不解决"听得懂"：
> 字幕写"锅盖"还是"锅盖儿"、写"晓得"不写"知道"，对听障用户是二次障碍。
> 需在 P1 前做一轮**方言字幕表达**的专门决策（是否做词汇映射/地区词表）。

## 二、说话人分离：技术上可行，但与"实时字幕"有结构性冲突

### 2.1 官方能力确认

sherpa-onnx **自带** `SherpaOnnxSpeakerDiarization` / `SherpaOnnxSpeakerIdentification`
Android 示例（上游 `android/` 目录），Python 侧 API 齐备：
`OfflineSpeakerDiarization` / `SpeakerEmbeddingExtractor` / `FastClustering`。

模型组成：

| 组件 | 模型 | 体积 |
|---|---|---|
| 语音分段（谁在说、说多久） | pyannote segmentation-3.0 int8 | **1.5MB** |
| 声纹嵌入（这是谁） | 3dspeaker eres2net_base_sv_zh-cn_3dspeaker | **39.6MB** |

### 2.2 端到端实测（官方 4分32秒多人对话音频 lei-jun-test.wav）

```
RTF = 0.241        （272.4s 音频，耗时 64.0s）
num_segments = 72
num_speakers = 3
```

分段边界清晰、时间轴合理（见实际输出，spk1/spk4/spk5 交替出现，每段 0.9–5.1s）。
**端侧完全跑得动**，RTF 0.24 远优于实时。

### 2.3 但它和"实时字幕"是两种东西——三个结构性冲突

1. **本质是离线批处理**：输入整段音频，输出"这段是谁说的"。
   实时字幕要的是"此刻谁在说"。要实时化，必须把音频**攒一段**再判——
   而攒多久，是**准确率与延迟的直接对冲**。攒 5 秒才能判出人，字幕就晚 5 秒。
2. **单麦克风位置决定成败**：一台手机放在桌上录两个人，是"混音"而非"分轨"。
   声纹聚类在这种条件下会**把同一个人切成两个 ID**（声线随角度/距离/遮挡变化），
   或把两个人合成一个。听障用户面对面场景恰恰就是单设备混音。
3. **ID 是"匿名的"**：聚类给出 spk0/spk1/spk2，但**用户不知道谁是谁**——
   除非让用户手动绑定（「这个是张三」）。这是纯交互成本，且每次会话都要重绑。

### 2.4 有一条真正优雅的替代路线（值得记下）

**双设备模式**：两台手机各放一个说话人面前 → 各自独立识别 →
在"本地"（无需服务器、无需云）做 ID 匹配 → 各自只显示对方说的话。

- 每台设备只需区分"是不是我"（二分类），而不是"这是谁"（多聚类）→ **难度大降**
- ID 匹配可用声纹嵌入在端侧比对，无需网络
- 精确度远高于单设备混音聚类
- **代价**：需要第二台设备 + 配对流程。存量听障用户家里不一定有第二台手机，
  且需要蓝牙/局域网通信（Wi-Fi Direct 或本地热点）

### 2.5 说话人分离的一句话结论

> **技术上完全可行**（官方示例齐全，RTF 0.24，端侧跑得动，238MB→实际 41MB 可接受）。
> **但与"实时字幕"是结构性冲突**：离线聚类 vs 实时出字、混音 vs 分轨、匿名 ID vs 已知身份。
> **不建议进 P0/P1**——它是另一个产品特性（会议纪要/双人对话），不是"字幕"的增强。
> 值得记下的优雅解是**双设备模式**，但它需要第二台硬件，门槛高于纯软件功能。
> 若将来做，前置条件是：①先验证单设备混音下的 ID 稳定性（听障用户真实场景录音）
> ②明确 ID 标注的交互方案。

## 三、对"只做一件事"的影响

| 问题 | 是否改变边界 | 结论 |
|---|---|---|
| 方言 | **是，必须处理** | 现用模型方言不可用（CER 57–79%）。这是**主场景缺陷**，不是新功能。解法：加一档方言模型 + 决策方言字幕表达方式。 |
| 说话人分离 | 否 | 技术可行但与实时字幕结构性冲突，属"会后纪要"那一侧（同上一轮的结论：归第二项目）。 |

**修订后的边界**：听幕 = 实时字幕（端侧离线、极大字、简单操作）。
方言必须支持（否则主场景塌陷），说话人不必支持（属于另一个产品的价值主张）。

## 四、决策记录（2026-10-30，用户拍板）

- **方案 A（可选下载方言包）有价值，但现在不做。** 触发条件 = 外部测试者反馈中出现"方言听不准"的真实需求。
- 届时的做法 = 设置页加一个"下载方言包"按钮（外挂式，APK 体积不变 93MB）：下载一个**多方言包**（首推 SenseVoice 237MB，一包覆盖 7 大方言+26 口音；川渝用户可再备 WenetSpeech-Chuan 238MB）到 `getExternalFilesDir()/models/`，模型列表自动出现"本机·"档（现有 `discover()` 已支持 sideload）。
- 落地前必须补的三件事（当前代码不支持）：①引擎加 `OfflineRecognizer` 支路（现有 `buildRecognizer()` 只建 OnlineRecognizer，方言模型全是离线-only，硬塞会加载失败）②VAD 切句后整句解码，可选"双 pass"（流式先出字、句尾方言包纠正）③下载需 INTERNET 权限 + 托管 240MB 模型文件，"完全离线"口径要调整；许可核对（TeleSpeech 社区许可别用）。
- 大部分用户不需要方言包——普通话主档保持默认、体积不变。
- **说话人分离**：不动，归第二项目（会后纪要）。

## 六、多人同时说话（重叠语音）实测（2026-11-02）

**问题**：多人一起说话、声音重叠时，单麦克风的现用模型会不会相互干扰？

**方法**：`bench/make_overlap.py` 把两个单人语音（`test_zh_16k.wav` 18.3s 说 A 话 + `test0.wav` 5.6s 说 B 话）按偏移混成 16k 单声道，喂现用模型 `small-ctc-zh-2025` 流式解码，对照各自单独的输出。

**结果**（final_text 对照）：

| 场景 | 结果 |
|---|---|
| A 单独 | 「各位好我们今天来测试一下听目的实十字幕功能把语音变成大字显示在屏幕上…」✅ |
| B 单独 | 「对我做了介绍那么我想说的是呢大家如果对我的研究感兴趣呢」✅ |
| **A+B 重叠，等响度**（3s / 6s 偏移） | 输出**与 A 单独完全一致**——B 的整段话被**完全丢弃**（winner-take-all） |
| **A+B 重叠，B 更响**（0.25 vs 0.75） | 重叠区**串字**：A 的「听目的实十字幕功能」被吞，B 的「给我做了介绍那么我想说的是…大家如果对…研究感兴趣」**插进 A 句子中间**——两句都不完整 |
| **A 说完 1s 后 B 说（不重叠）** | 两段都完整、按顺序识别 ✅ |

RTF 不受影响（0.03–0.05），不会卡死崩溃——只是**内容错漏**。

**结论**：
1. 单麦克风物理上收到的是混合声波，现用模型**没有声源分离能力**——同时说话必然干扰：等响丢人、响度接近串字。
2. **轮流说话（不重叠）完全没问题**——这正是听障面对面沟通的自然节奏。
3. VAD 在混合音上持续判"有声"，端点不会在两人之间切开，字幕会把重叠部分糊成一段。
4. **实用建议**（可写进产品 FAQ）：多人场景尽量一次一人说话；手机放近说话人（实测响的那个赢）。
5. 根治路线已在 §二 调研：双设备模式 / 离线说话人分离（pyannote+3dspeaker 实测 3 人 72 段分得清，但离线批处理与实时字幕有延迟冲突）——均不在 v1。

## 七、方言包做"方言版"的可行性实测（2026-11-03，v1.5 后用户追问）

**问题**：方言模型只能整句出字（离线），有没有流式方言模型？有没有办法降低延迟？

**结论：没有流式方言模型。** sherpa-onnx 全部方言候选（SenseVoice / TeleSpeech / WenetSpeech-Chuan paraformer）都只有 OfflineRecognizer；官方也没有流式方言 ASR。这是模型生态现状。

**实测（同批音频，Mac）**：
| | 普通话18s | 英文 ABC/PDF | 四川 | 天津 | 河南 | 大小 | RTF |
|---|---|---|---|---|---|---|---|
| SenseVoice int8-2025-09-09 | 好（2处错字：听目/厅障） | **能读**（少量错字） | 好 | 开头错 | 好 | 233MB | 0.11-0.14 |
| paraformer-Chuan int8-2025-10-07 | **全对（0错字，听幕/听障都对）** | **字母乱码，不行** | 好 | 近乎完美 | 好 | 231MB | 0.08-0.09 |
| 双语版 x-asr（现用） | 中（听账） | 好 | 中 | 中 | 中 | 162MB | 0.10 |

**降延迟三方案**：
1. **双 pass（推荐）**：流式模型先实时出字 → VAD 切句后方言模型重解码该句纠正字幕。感知=实时+句末修正。代价=内置双模型（25MB+233MB → APK ~300MB）、双模型功耗。
2. **VAD 短语切分**：按 0.4-0.6s 停顿切短语，每短语整句解码；延迟≈短语时长+解码（手机 1-2s）。短句体验接近实时，长句仍慢。
3. **官方"模拟流式"**（sherpa-onnx `simulate-streaming-sense-voice-microphone.py` 实证）：滚动窗口重解码整个缓冲（VAD max_speech 8s 截断）+ 显示中间结果。首字快但文字反复跳、CPU 持续高。

**方言版选型建议**：SenseVoice（一包覆盖方言+普通话+英文+粤语）；paraformer-Chuan 普通话最准但不懂英文，只适合川渝专版。

## 八、定案：方言版选 SenseVoice（2026-11-03）

用户比较两个方言模型后拍板："选 SenseVoice，再做个 1.5 版本的方言版"。

- **选型理由**：SenseVoice 方言覆盖面更宽（含粤语）+ 能认英文 + 自带标点/ITN；Chuan 普通话更准、天津话近满分，但**不认英文**且只覆盖川渝方向。作为"方言应急版"，覆盖宽度优先。
- **形态**：VAD 切句 + 离线整句识别（无流式方言模型可用），**说完一句约 0.6s 停顿后整句出字**。这是"能听方言"的代价，已在 README 明确写清。
- **实测（Mac/模拟器）**：RTF 0.24（x86_64）；四川话样本 CER 远优于原流式模型；普通话比双语版略逊（2 处错字），英文可用，粤语可用。
- 双 pass（流式先出 + 离线纠错）是后续可选升级，本期未做。

## 九、双 pass 落地 + 标点（2026-11-03，v1.6）

- 方案一（流式先出 + 离线重解码纠正）已实现：方言版三模型 = small-ctc 25MB（第一遍）+ SenseVoice 237MB（第二遍）+ CT-Transformer 标点 75MB。
